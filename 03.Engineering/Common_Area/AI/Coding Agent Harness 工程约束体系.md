# Coding Agent Harness 工程约束体系（认知 · 代码库 · 验收三层）

> 来源：知乎回答《大家是怎么构建用于编程的 harness 的？》（作者：潘锦，2026-11-25 抓取）。本文是**提纯版**：只留决策规则、优先级、清单与易错点，论证与原文表述见 [`98.Raw/2026-11-25-zhihu-coding-harness.md`](../../../98.Raw/2026-11-25-zhihu-coding-harness.md)（两者冲突以 raw 为准）。

## 一句话结论

**真正的极速建立在极致的确定性约束之上。** 把约束从「自然语言规则」下沉到「架构 / 类型 / Lint / 测试 / 日志 / 形式化验证」，让错误在物理上不可能发生或在编译期就报错；自然语言（AGENTS.md、Skills）只留给无法编码的主观权衡。没有提示词秘籍，只有软件工程基本功在 AI 时代重新绽放。

## 一、问题背景：同一套工具，两种结局

| 场景 | 观察 |
|---|---|
| 参照团队（Lauren Tan，AI Engineer CODE 2026 分享） | 个人 3,000 PR/月、团队 11,000 PR/月、每日发稳定版、200+ 跨团队成员提交；相对回滚率稳定 ~0.5%；客户端启动/打字/会话切换性能反而更快 |
| 作者团队（引入 Codex / Claude Code 后） | 生成速度翻数倍，产品经理一天 15 万行，一个月做出个 Agent；但故障率上升，出现「客户端升级后无法启动」 |

差异不在工具，在于**是否把每个踩过的坑固化成确定性检查**：每出现一个问题，就变成一个强制检查的工具或 lint 规则——而且**业务层规则比代码规范层更多**。

## 二、三层结构

| 层 | 要解决的问题 | 载体 |
|---|---|---|
| 个人认知 | 团队怎么看待「用概率机器约束确定性系统」 | 投入优先级、纠偏机制、对自动化的克制 |
| 代码库治理 | Agent 拿到的最大上下文输入源 | 目录结构、注释、日志 |
| 验收逻辑 | 「符合业务意图吗、真的有 Bug 吗」 | 功能地图、可调用工具、深度验证、监控告警 |

## 三、投入优先级（从高到低，严格按序）

| 优先级 | 手段 | 给人的感觉 | 说明 |
|---|---|---|---|
| 1 | **代码架构与 API 设计** | 最慢见效 | 用接口封装与架构边界**从物理上消除犯错的选项**（错误的调用方式根本不存在） |
| 2 | **确定性静态检查** | 传统工程活 | 类型系统、编译器、自定义 Lint、单元测试，机械化拦截违规 |
| 3 | **运行时与形式化验证** | 成本高但边际成本已逆转 | 让代码真跑起来，检查系统不变量与业务意图是否对齐 |
| 4 | **自然语言规则**（AGENTS.md / Skills） | 改起来最快 → 最容易被滥用 | 只留给无法编码、需要主观权衡的场景 |

> ⚠️ 最常见的误区：**第 4 层是大家改得最多的，恰恰应该是改得最少的。**

## 四、纠偏三问（可执行规则）

发现线上问题 / Agent 重复犯同类错误时，**禁止直接去改 AGENTS.md**，必须依次自问：

1. 能不能改底层 **API 设计**，让这个错误的调用方式根本不存在？
2. 如果不能，能不能写一条 **AST / Lint 规则或类型约束**，让它在编译期直接报错？
3. 前两条都做不到 —— 这真的是需要主观判断的**软性规范**吗？是，才写进 AGENTS.md。

| 判断 | 落点 |
|---|---|
| 错误调用能设计成不合法 | 架构 / API 签名 |
| 能静态检测 | Lint（含 AST）、类型、单测 |
| 只能跑起来才知道 | 运行时检查、集成/属性测试、监控 |
| 纯审美与权衡（命名分寸、权衡取舍） | AGENTS.md 一句话 |

### 跨工具迁移：为什么「下沉」同时解决可靠性与迁移成本（本次消化批注，非原文）

「跨工具迁移」的答案藏在这个优先级里：先分清两个轴——**寄存位置（写在哪）** 与 **强制力来源（谁执行）**。

| 约束写在哪 | 强制执行者 | 换 Agent 工具（Codex→Claude Code→DSH→opencode） | 换技术栈（Vue→React） |
|---|---|---|---|
| 架构 / API 签名 / 模块边界 | 编译器、打包器 | **零改动** | 要改 |
| Lint 规则、自定义检查器 | `make check` | **零改动** | 要改 |
| 单测 / 属性测试 | 测试框架 | **零改动** | 要改 |
| TLA+ / Lean 规格 | 模型检查器 | **零改动** | 通常零改动 |
| AGENTS.md / Skills / 斜杠命令 / hooks | 模型「自觉」+ 工具加载机制 | **必须复制、改写、重新调参** | 零改动 |

> 第 4 层是**整层**工具相关资产：AGENTS.md、Skills、斜杠命令、hooks、子代理定义、权限模型；MCP 算准标准（协议统一，传输方式 / 工具命名空间 / 鉴权仍各不相同）。不要只说成「AGENTS.md」。

**「漂移」漂的是什么**：不是文件搬不动（复制粘贴即可），而是**同一段文字在不同工具上行为不等价**。

| 漂移类型 | 机制 |
|---|---|
| 格式漂移 | 发现机制各异：`CLAUDE.md` / `.cursor/rules/*.mdc` / `.github/copilot-instructions.md` / `AGENTS.md`；向上查找、`@import`、全局层支持各不相同 |
| 预算漂移 | 同一份长规则，在不同工具的上下文裁剪策略下被截掉的部分不同 |
| 位置漂移 | 有的注入 system，有的当 user message，遵守率不同 |
| 语义漂移 | 规则互相冲突时模型随机挑一条执行；换模型/版本，遵守率随之变化 |

而 Lint 规则漂不漂，跑一次就知道——**第 4 层没有可断言的「通过」**。

**判定三问**（决定一条规则该不该停在第 4 层）：

1. 违反它时，是**机器变红**，还是靠人或模型发现？后者 = 没下沉到位。
2. 把 AGENTS.md 整份删掉，这条还成立吗？成立 = 下面已有更硬的层兜底，这句文字是冗余的。
3. 明天全团队换成另一个 agent 工具，这条要重写吗？要 = 它是工具耦合资产，值得先问「能不能沉下去」。

**同一个坑的三种写法**：

| 坑 | 停在第 4 层 | 下沉后 | 换工具时 |
|---|---|---|---|
| 渲染进程误引主进程模块 | AGENTS.md 写「禁止」 | `eslint-plugin-boundaries` / 拆包使物理不可 import | 文字要重写且可能被无视；规则一行不动 |
| 向主分支 force push | AGENTS.md 写「不要」 | pre-push hook / 服务端分支保护 | 同上 |
| 日志字段不规范 | 文字规范 | logger 封装 + 字段白名单检查 | 同上 |

> **一句话**：约束下沉不是为了「更严格」，是为了「换成别的执行器时它还在」。能被代码库自己执行的约束，不依赖任何执行器。
> 推论到规则取舍上：**有对错的**（能不能 import、字段名对不对、能不能 force push）下沉成机器判定；**只有偏好的**（提交粒度、命名口味、先测试还是先实现）才配待在 AGENTS.md。对有对错的事写文字规则，等于用建议冒充法律。

## 五、克制自动化

- 不要一上来搞「全自动软件工厂」（多 Agent 编排外环：自动接单 → 自动写码 → 自动上线）。
- **自动化程度越高，产生的垃圾越多，账单越贵。**
- 先把确定性约束做好，是所有自动化的前提。

## 六、代码库治理清单

### 6.1 目录结构：直白命名 + 强硬依赖阻断

| 动作 | 具体做法 |
|---|---|
| 用目录名直接传达上下文语义 | 顶层就分 `electron-main/` 与 `electron-renderer/`；后端明确分领域层 / 基础设施层 |
| 用工具禁止跨边界引用 | 前端 `eslint-plugin-boundaries`、Java `ArchUnit` 等依赖图分析 |

> 典型事故：Agent 缺全局架构视野，把主进程代码引入渲染进程 → 界面卡顿掉帧。

### 6.2 注释：小心 Agent 写的注释

| 风险 | 机制 |
|---|---|
| Agent 偷懒把逻辑写进注释 + 给快速实现甚至 mock；人类扫代码会跳过注释，**AI 会认真读并当成正确实现扩散** | 注释会过期，且**永远无法被编译器强制执行** |

| 做法 | 强度 |
|---|---|
| 禁用绝大部分注释（Lauren 团队约 99%） | 激进 |
| 严格清理「解释型注释」（为劣质代码找借口的那种），并用定制 Lint 检查注释 | 作者团队采用的折中 |

### 6.3 日志：给闭环一份「运行时事实源」

目的不是让日志适配 Agent 的解析能力（Agent 读日志已经很强），而是**消除运行时黑盒**。三类消费者各有要求：

| 消费者 | 需要日志提供什么 |
|---|---|
| 开发 / 排障 Agent | 验证证据：实际命中的业务分支、状态流转、数据变更；最好能定位到代码行与调用链（调用链可由链路系统经 MCP 提供，成本考虑） |
| 监控告警系统 | 稳定字段 + 错误码，供实时指标聚合与异常告警 |
| 人类工程师 | 告警后顺着清晰脉络秒懂「发生了什么」，据此决定回滚或修复 |

## 七、验收清单（最耗时的环节）

### 7.1 现状判断

- 每天几百个 PR 时，高级工程师逐行看 Diff 已不可行；作者团队**基本不再做人工 Code Review**（作者本人偶尔抽查核心链路，或让 AI 汇报链路现状）。
- 验收不是「更努力地看」，而是**给 AI 更好用的工具**，而不是原始工具。

### 7.2 四项建设

| 建设 | 内容 | 反模式 |
|---|---|---|
| 功能地图 | 结构化描述产品有哪些功能；**统一人与 AI 的业务词汇** | 让 Agent 自己猜业务 |
| 可调用工具 | CLI / MCP，让 Agent 自动操作界面与功能、观察日志与结果 | ❗每次验证都现场手搓测试脚本（既贵又慢还不稳定） |
| 深度验证平民化 | TLA+（多端并发模型检测）、Lean（证明核心算法不抖动）、UI 属性测试（随机生成海量交互序列找边界 Bug） | 认为「业务团队用不起形式化验证」（AI 已让编写成本暴降） |
| 监控告警 | 告警逻辑与 AI、日志、代码打通：快速定位 → 给方案 / SOP → 甚至自愈；当前仍需 SRE / 开发人工确认 | 只告警不闭环 |

## 八、反方观点（保留矛盾，勿静默删除）

评论区高赞（赞同 1）：「其实没那么复杂，好的工程架构不需要额外的很多 harness，我们开源项目全部 AI 开发，50w 行代码，平时开发很随意和 AI 聊就行，基本都是一句话搞的需求。」

- 可解释为：**架构足够好时，harness 的边际收益很低**——与本页「优先级 1：架构从物理上消除犯错选项」并不冲突，只是把权重全压在 1、2 层。
- 待验证：该说法缺少回滚率、故障率等对照指标，不宜直接作为「不需要治理」的依据。

## 九、易错点

1. **把 AGENTS.md 当万能补丁**：每踩一坑就写一条规则 → 规则膨胀、互相冲突、且不具强制性（用建议冒充法律）；换工具还得整份重调。先走三问。
2. **只加规则不加检查**：业务层规则尤其如此，必须落成强制检查（作者团队业务规则数量 > 代码规范规则）。
3. **迷信自动化外环**：吞吐提升但垃圾同比例放大，账单更贵。
4. **让人类继续当人肉 Diff 阅读器**：几百 PR/天时这条路直接失效，要投资验收工具链。
5. **忽略注释的反向传染**：注释是 Agent 的「学习材料」，劣质注释会被当成范式复制。
6. **日志只为人写**：缺稳定字段/错误码，Agent 与告警系统都用不上。

## 十、可迁移到本工作流的动作（本次消化批注）

- **给 AGENTS.md 做减法**：本库 `AGENTS.md` 与各项目规则里，凡是「能用脚本/检查器判定的」条目（如「提交前扫描敏感信息」「tags 禁止空格」），优先落成脚本或 lint，而不是只写在规则里。
- **错误复用即工具化**：同一个坑踩第二次时，先问「能不能做成一条检查」再动笔写规则。
- **验收给工具而非脚本**：为常用验证路径准备现成 CLI / MCP（本机已有 zhihu-mcp、DSH 工具链），避免每次临时拼命令。
- **目录即文档**：新增子目录时用直白名字承载架构语义，比在 AGENTS.md 里补一段说明更可靠。

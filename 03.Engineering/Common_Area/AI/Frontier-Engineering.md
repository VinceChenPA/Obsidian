# Frontier Engineering（前沿工程）

## 核心命题

软件开发正在分化为两类人：**改变了与 AI Agent 协作方式的人**，和**只是换了编码工具的人**。

具备跃迁式生产力提升的开发者并非用了更好的工具，而是工作方式不同了——**他们不再直接构建软件，而是构建"构建软件的 Agent 系统"（agent setup that builds the software）**。

- AI Agent 已能自主写代码、跑测试、修失败、迭代，越来越多场景下可连续工作数小时无需人类输入。
- 这不是 vibe coding，也不是往聊天框里粘贴提示词碰运气；而是一门**有纪律、有方法论的实践**：用 AI Agent 的杠杆放大工程严谨性。
- 这是一项**工程投资，不是开关**：前几周会更慢（写 steering 文件、重构代码库、学习为 Agent 拆解任务），之后才会显著加速。
- 长期来看，需要持续锻炼的核心技能是**管理自己的注意力**：在多 Agent 间切换、在一切加速时仍守住质量底线、并克制深夜查岗的冲动。工作本质是反复决定"什么需要我关注、什么不需要"。
- 目前仍处早期采用阶段，尚无人完全解决"如何最有效地审查 Agent 产出"、"如何为 Agent 而非人类设计工具与测试设施"等问题。

## 十条原则（Drilldown）

### 01. 你是架构师，不是打字员（You are the architect, not the typist）

工作不再是写代码，而是**写意图（writing intent）**。前沿开发者亲手写的代码不足其产出的 1%，其余来自他们指导、掌舵、审查的 Agent。

工作归结为两件事：
1. 定义"完成"是什么——需求、约束、验收标准；
2. 验证产出是否符合意图。

**清晰意图的写法**："给这个 API 加鉴权"不是清晰意图；说明哪些角色能访问哪些端点、token 过期时发生什么、如何测试未授权访问，才是。然后让 Agent 去写代码。

时间分配从"大部分时间写代码"变为"花在意图、方向和对 Agent 产出的针对性审查上"。

### 02. 最大化 Agent 时间，最小化你的参与（Maximize agent time, minimize your involvement）

反模式：始终在环里——提示 Agent、等 60 秒、拿回代码、手动测试、把报错粘回聊天框、循环。这样永远达不到高速度。

正确做法：
- 给 Agent **更长的任务 + 内置的清晰验证步骤**，例如："实现此功能、写测试、运行测试、确保通过、新代码覆盖率达 90%"。
- Agent 工作 30 分钟以上时，你去做别的事。Agent 中途出错没关系，让它继续循环、自我纠错、收敛到正确答案。
- **并行运行多个 Agent**，异步审查产出。生产力的瓶颈不再是打字速度，而是你能让多少个 Agent 同时有意义地忙碌。
- 进阶：让 Agent 运行数小时乃至过夜、让 Agent 启动其他 Agent、第二天早上看结果。目标是逐步把自己移出环，直到你的参与仅限于**设定方向 + 验证结果**。

### 03. 为 Agent 构建代码库（Build your codebase for agents）

Agent 的水平受限于它所工作的代码库。先做对人类同样有益的基建：完善的 README 与架构文档、描述预期行为的测试、清晰的模块边界、强类型、快速构建与信息丰富的报错。

- 在大型遗留代码库中：**逐个模块改造**，并把 Agent 限定在你已准备好的模块里，而非直接指向整个 repo。
- 这项投资的 ROI 更高了，因为人类新成员只入职一次，**而 Agent 每个会话都要重新入职**。
- Agent 需要人类脑中默认携带的显式上下文：定义约定与编码标准的 **steering 文件**、按需加载的任务级流程 **skills**、自动化环境搭建的脚本、以及检索上下文与执行操作的命令行工具和 **MCP server**。
- **让 Agent 为未来会话记录自己的工作**：记录设计决策、写充分的代码注释作为持久记忆，让下一个 Agent 会话继承代码背后的推理，而不只是代码本身。

### 04. 给 Agent 快速反馈闭环（Give agents a fast feedback loop）

如果 Agent 不能在你介入前本地跑测试并自我纠错，**你就是瓶颈**。前沿开发者大力投资让验证**快、本地化、可自动化**，使 Agent 能在紧密循环中测试。

Agent 应当能访问：
- linter 和单元测试；
- 浏览器（渲染并目视验证 UI 改动）；
- 依赖服务的本地 mock（集成测试）；
- 在笔记本上拉起完整技术栈的能力（端到端测试）。

原则：**凡是你自己用来验证工作的工具，Agent 也要能用**，让它自我验证，而不是由你在工具间复制粘贴输出。

**基于属性的测试（property-based tests）**尤其有价值：验证实现是否符合意图，并捕获 Agent 想不到写的显式用例的边界情况。

不投入的后果：更快的代码生成只意味着更多坏构建和 bug。投入之后整体质量反而提升，因为 Agent 验证得比很多人类更彻底、更一致。

### 05. 执行很便宜，方向就是一切（Execution is cheap. Direction is everything.）

当代码一下午就能写完，难点不再是实现，而是**搞清楚要解决什么问题、构建什么、何时改变方向**。实现细节便宜，系统设计、API 契约、依赖、架构权衡则不便宜——把精力花在这些持久决策上。

- 设计阶段把 Agent 当**头脑风暴伙伴**：研究选项、探索替代方案、戳穿你的思路。
- 两个设计都可行时，**让 Agent 各自做出原型对比**——过去靠辩论定夺的选择，现在可以靠证据定夺。
- 方向确定后，践行 **spec-driven development（规范驱动开发）**：与 Agent 协作写出清晰 spec 与需求以降低歧义。给 Agent 模糊提示，它会自行决定权衡取舍，你之后撤销这些选择的时间会超过省下的写 spec 的时间。
- 迭代过程中把注意力放在最重要的事上：架构在真实负载下是否站得住、是否需要重新评估设计权衡、东西是否已能交到用户手上。

### 06. 把代码当作一次性产物（Treat code as disposable）

代码现在很便宜。持续评估"正在构建的东西是否值得发布"，以及发布后随之而来的运维与维护成本。可以花一天做个原型然后走人，也可以两周做到接近生产级、发现产品方向不对就推倒重来。

过去弃代码难有两个原因：亲手写了数月有感情；重来意味着再干数月。**这两个理由现在都消失了**。重要的是发布对的东西，而不是把初稿硬撑到生产、或因沉没成本回避重构。

不服务于你的代码就扔掉——Agent 可以在今天之内建出下一个版本。

**例外：边界上的测试**。单元测试随代码一起丢弃；让"重来"变得安全的测试要保留：**端到端集成测试（行为）、基于属性的测试（不变量）、负载测试（规模下的性能与并发）**。它们共同构成任何重写都必须满足的契约。

### 07. 以人类标准要求 AI 产出（Hold AI output to human standards）

没有质量的速度只是把更多风险送进生产。**你署名发布的代码，无论由谁（或什么）生成，你都得负责**。

- 早期：逐行审查 Agent 产出，建立"模型哪里对、哪里错"的直觉。
- 之后：逐行读不可扩展，于是构建 **AI reviewer** 分担——检查团队在意的点：正确性、安全性、可维护性、测试质量、常见 bug 模式。在**本地变更提交 PR 前**跑一轮 AI 审查，在 **CI 里再跑一轮**。随着 AI reviewer 成熟，让它处理前几轮反馈。
- 人类注意力集中在最擅长判断的地方：设计与架构是否正确、变更对上/下游系统的影响、安全边界是否可靠。
- **把 Agent 循环延伸到合并之后**：让 Agent 监控部署、验证生产行为，出回归就自动开始修复。对结果负责意味着陪伴变更直到生产，而不是止步于 PR。

### 08. 信任边界，不是信任 Agent（Trust the boundaries, not the agent）

让 Agent 长时间自主运行，需要**不依赖你盯梢的护栏**。不要接受错误二选一——要么让 Agent 在笔记本上撒野，要么每次工具调用都要你点"接受"。

做法：约束 Agent 的文件、工具、网络、凭证访问，只给它真正需要的，然后让它无监督运行。
- **先从窄范围开始，随信心建立逐步放宽**，直到只对"无法撤销的动作"设闸。
- **对生产环境格外偏执**：Agent 绝不应接触生产账号或部署凭证，除非你明确、刻意地授予。
- 叠加**确定性检查**，捕捉常规测试大概率发现不了的问题：SAST（静态应用安全测试）标记漏洞、凭证扫描捕捉泄漏的密钥、自动化推理（automated reasoning）用数学方法验证 Agent 产出符合意图。
- **每自动化一条护栏，就少一个让你留在环里的理由。**

### 09. 一切皆可用 Agent，不只是代码（Use agents for everything, not just code）

习惯与基建建立后，把同一模式应用到一切地方：过去要一周的设计文档现在一下午；数小时的运维排查现在几分钟；状态更新、sprint 总结、oncall 报告、文档——全部遵循同一流程：

> **提供上下文 → 定义结果 → 让 Agent 起草 → 审查打磨后再分享给他人。**

真正的加速来自**把 Agent 用在整个开发生命周期**：规划、开发、测试、部署、运维。这本宣言的一切同样适用于这些 Agent：清晰的意图、快速的反馈闭环、受限的访问。流水线 Agent、oncall Agent、文档 Agent、第三方 Agent 应共享大部分相同的 setup 与上下文——**给它们同样的 steering 文件和工具**，使它们无论执行什么任务都行为一致。

### 10. 持续调优你的 Agent 配置（Continuously tune your agent setup）

**每当 Agent 走错路或不必要地把你拉进环里，都问自己：如何防止它再次发生？** 答案可能是：

- steering 文件里的一条新规则；
- 一个 skill，固化了它做错的流程；
- 一个自动化手动步骤的命令行工具；
- 一个获取正确上下文的 MCP server；
- 对之前设限的工具/系统放宽访问。

**每一次 Agent 犯错和打扰你，都是把它的自主性再推远一步的机会。**

这是前沿工程的日常习惯：**你不只是在构建产品，你在持续改进"构建产品的系统"**。这个习惯会复利：
- 起点：只有显式提示才运行、频繁需要你输入的 Agent；
- 成熟后：Agent 更自主，可在后台运行——主动发现并修复 bug、清理技术债、改善代码质量，无需你发起任务。
- 模型升级后，**新模型能清理旧模型留下的问题**；新模型发布时，重新评估为旧模型弱点做的 workaround 是否还需要。**steering 文件和工具是与模型同步演进的活文档。**

## 落地启示（结合本库实践）

1. **本库的 AGENTS.md + MOC + log 体系正是"为 Agent 构建代码库"的实例**——每个会话 Agent 都要重新入职，显式上下文决定产出上限。
2. **穷尽式提问（grilling）≈ 原则 05**：方向与权衡在编码前用证据和对话钉死。
3. **入库/归档工作流本身就是原则 09**：一切非代码任务也走"上下文 → 结果 → 起草 → 审查"。
4. **每次 Agent 出错后补写规则/技能，而非手动纠错**——原则 10 的直接可执行版本。
